Design Systems

Bricks design system

Bricks didn't start as a design system. It started as a reimagining of the platform: new layouts, new interactions, and a hard look at whether the old visual language still worked. Then we took it a step further and moved it into GIT, so the team could prototype on the real thing and ship 1.7× faster.

RoleDesign System Specialist
FocusComponents · AI guideline · GIT
CompanyHousing.com

The challenge

We needed a shared design language, and we needed it fast.

As we moved toward a new product experience across teams, we had to keep experiences consistent while giving every team a foundation to build and scale from, without compromising design quality along the way.

My role

As the design system specialist, I helped establish the new design language and its foundations, and defined what the core component layer should look like.

I also wrote the guidelines that let the team use AI to build components faster, and consistently.

Scaling with AI

Scaling component creation with AI

Instead of prompting AI from scratch for every component, I created an MD guideline that encoded our design rules and decision-making framework.

Define the rules

Documented the design language, component principles, do's and don'ts, properties, states and expected behaviours.

Guide the AI

The guideline also defined what AI should clarify when a designer's prompt was incomplete, instead of making assumptions.

Build with consistency

The team used the guideline alongside their prompts to generate the initial core components faster, while staying aligned with the system.

Design review

Generated components were reviewed and refined by designers before becoming part of the core system.

The goal wasn't to automate design. It was to automate the repetitive decisions so designers could focus on the quality of the system.

04 Bricks, in code

We stopped redrawing the system, and moved it into GIT

Why GIT

The same work, again and again

A system that only lives in Figma still has to be rebuilt by hand, every single time.

Scaling Bricks was still manual.

Every new component, variant or token change meant redrawing it in Figma, re-explaining it in handoff, and waiting for engineering to rebuild it. Prototypes were static mockups that only looked like the product.

So we made GIT the single source of truth.

Tokens, the DESIGN.md guideline and the core components moved into a repository. Designers could now vibe-code quick prototypes with Claude and Cursor, built from the real tokens and components, so what stakeholders clicked through was close to the real system, not a picture of it.

  1. Figma foundationsColour, type, spacing, radius
  2. Tokens + DESIGN.mdCommitted to GIT
  3. Coded componentsBuilt once, reused everywhere
  4. Vibe-coded prototypeClaude & Cursor on the real system
  5. Stakeholder go-aheadApproved on something clickable
  6. ShipLess rebuilding, less back-and-forth
